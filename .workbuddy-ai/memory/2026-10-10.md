## 关键设计（详见 ADR-040）

1. 文档从 `indexing` 开始，**promote 是唯一进入 `available` 的路径**。
2. `activate()` 把状态与 active 版本写在同一条条件 UPDATE 里 → 二者不会出现不一致中间态，`deleted` 永不被重新激活。
3. `mark_failed()` 带 `active_index_version IS NULL` 守卫 → **失败的重建索引不降级**仍在服务旧版本的文档。
4. 重复上传报告真实状态（G20），且仍不 dispatch。
5. 删除接受任何非 `deleted` 状态 → 坏文档可自愈。
6. **不做数据迁移**：早于本改动的 `available` + `active_index_version=NULL` 行保留原样，重复上传为它报 `failed`，可删除。

## 踩到的坑 / 新发现

1. **UI 验收脚本的等待逻辑有 bug（假失败）**：`waitForFunction(() => assistant 数量 > 0)` 在会话已有历史答案时立即返回，读到的是**上一条**答案的引用（0 条）。必须记录发送前的数量，只等新增的那条。
2. **演示库被测试夹具污染，且部分夹具的版本不兼容当前 embedding**：库里有 `deterministic/deterministic-hash/dim=64`（旧/测试 provider）与 `siliconflow/BAAI/bge-m3/dim=1024`（真实 provider）两套版本。**对 deterministic 版本的文档做作用域检索 → 全部候选版本不兼容 → `retrieval_unavailable` → 用户看到「Knowledge retrieval is temporarily unavailable」**，而这个文案是误导的（真实原因是索引用了别的 embedding 模型）。这是本次发现的新问题（需要新错误码 + Change ID 才能改）。
3. **`test_document_scope_live.py` 泄漏他人文档夹具**：每次运行留一个 `foreign.md`，已累积 5 个。副作用：本改动之前它们是 `available`（进授权集合、进选择器）；改动后是 `indexing`（**被正确排除**）——我的改动顺带降低了这个泄漏的危害。已修掉泄漏。
4. **`app.state.container` 只在 lifespan 装配** → `TestClient` 必须当上下文管理器用。
5. **e2e / 浏览器脚本必须 `NO_PROXY=127.0.0.1,localhost`**，宿主 `HTTP_PROXY` 会把本机请求变成 404。
6. 前端镜像重建在本次 `up -d --build backend frontend` 中**没有**用 `--no-cache`，但服务哈希与新构建一致（`index-DFrkUPRh.js`），本次未复现缓存问题。
7. 用 Python heredoc 做长文本替换时，含 `\\|` 与引号的内容会让 bash 解析失败 → 改为**写临时 .py 文件再执行**。
